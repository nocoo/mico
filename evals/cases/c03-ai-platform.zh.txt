今天我用十分钟介绍我们这套 AI 白板系统的架构，从前端到后端，再到模型和语音，一条链路讲清楚。大家可以在白板上跟着我画，最后我会把关键取舍和风险总结出来。

先从用户看到的部分说起。浏览器里是一个 React 应用，画布用 SVG 渲染，所有的图形、文字、便签、框架和连线都是数据驱动的。用户拖动一个矩形，前端先产生一个本地预览，再把操作发给后端。为了保证多人同时看同一块白板，前端维护一个版本号，后端返回新版本后，前端才确认这次修改。这里最重要的设计是：界面永远先响应，网络请求在后台排队。

前端之上是 Vite 开发服务器，生产环境可以是任意静态服务器。开发和本地使用时，Vite 把 /api 请求代理到后台的 Node 守护进程。AI 对话走 /api/ai/chat，返回的是流式的 UI message，不是一次性 JSON。语音转写走 /mai/realtime，由 Vite 的 WebSocket 代理转发到 Azure 的转写服务。这样浏览器只和同源地址通信，不会遇到混合内容和跨域问题。

后台是一个 Node 守护进程，负责三件事：第一，管理多张画布和当前激活的画布；第二，把所有画布操作原子化地写入 SQLite；第三，通过 WebSocket 把变更广播给所有打开的浏览器。每张画布有自己的版本号，批量操作要么全部成功，要么全部失败，避免画到一半留下半成品。每次写入之后，后台广播一个 board 事件，里面包含画布信息、版本号和完整图形列表。

AI 这一层是关键。浏览器把用户消息和当前框选的对象发给后台，后台把画布压缩成一份结构化上下文，再交给 AI SDK。模型不是直接改数据库，而是通过工具调用：读画布、加文字、加便签、加形状、连线、加框架、画曲线、加 HTML 卡片、更新和删除。每个工具在后台执行，执行完立刻写库并广播。也就是说，模型一边说，用户一边看到图形出现。这里有一个很重要的边界：模型只能通过工具操作画布，不能直接执行任意代码。

再往上是模型网关。我们本地用 Magpie，它兼容 OpenAI 的 Chat Completions 协议，默认模型是 GPT-6 Luna。AI SDK 负责把工具定义转换成模型能理解的 schema，处理流式返回，并在模型调用工具后把结果喂回去，让模型继续下一步。为了防止模型画到别的画布，后台在处理一次 AI 请求时会把 canvasId 固定下来，后续所有工具都写这张画布。

语音这一层是另一条链路。课程音频在浏览器里解码成十六 k 单声道 PCM，按时间片送给转写服务。客户端的能量检测判断一句话有没有说完，静音超过阈值就提交一段。转写结果按段落进入 AI 队列，队列一次只允许一个请求，AI 落后时会把最多三段合并，避免积压。如果一句话没说完，模型可以只回复 WAIT，不画东西。

最后说取舍。第一，我们选择了本地优先：SQLite 加本地 daemon，部署简单，但多机协作需要额外的同步层。第二，我们选择了服务端执行工具，安全和一致性更好，但模型每一步都要经过后台，延迟比前端直接执行高。第三，我们选择了流式事件而不是轮询，实时性更好，但消息顺序和断线重连要小心。第四，画布用完整快照广播，代码简单，画布很大时要考虑增量同步。

风险主要有三个：模型生成的布局可能重叠，需要读画布和更新工具来纠正；语音转写会断句错误，需要允许 WAIT 和合批；长会话的上下文会越来越大，需要压缩历史或者只保留最近的关键操作。下一步先做布局检查和总结卡片，再做多人权限和增量同步。今天的架构就讲到这里。
